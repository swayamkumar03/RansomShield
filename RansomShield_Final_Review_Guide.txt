SECTION 1: PROJECT OVERVIEW

1. Project Title:
   RansomShield — Real-Time Behavioural Ransomware Detection using Shannon Entropy
   and Multi-Factor Anomaly Scoring.

2. One-Line Project Definition:
   RansomShield is a concurrent Java 21 desktop security application that monitors
   the local filesystem in real time, computes byte-level Shannon entropy, detects
   anomalous file modification bursts and suspicious renames across a sliding time
   window, calculates a 0-100 behavioural threat score, and executes safe simulated
   incident response and sandboxed quarantine.

3. 60-to-90-Second Spoken Pitch (Speak directly to professor):
   "Good morning, Professor. Traditional antivirus programs rely on static signatures
   — such as file hashes — which fail against zero-day and polymorphic ransomware
   because the binary signature changes with every attack. RansomShield takes a
   behavioural approach. Using Java NIO WatchService, it monitors filesystem activity
   in real time on a background thread. For every modified, created, or renamed file,
   it computes Shannon byte entropy to measure data randomness.

   Crucially, RansomShield does not rely on entropy alone. High entropy alone could
   simply be a legitimate ZIP archive or MP4 video. Instead, our BehaviorDetector
   tracks four additional signals across a sliding time window: file modification rate,
   total unique files touched, directory traversal span, and suspicious extension
   renames. These metrics feed into our ThreatScoreEngine, producing a unified
   0-to-100 threat score categorized into NORMAL, SUSPICIOUS, HIGH, and CRITICAL.

   When malicious behaviour is detected, our Active Defence and Incident Response
   system raises in-app and desktop notifications, logs the incident in SQLite via
   JDBC, and executes safe simulated containment by default, protecting user data
   from accidental corruption. The entire application is built on Java 21, leveraging
   multithreading, thread-safe concurrent queues, JavaFX, and JDBC."

4. Problem Statement:
   Ransomware is malicious software that encrypts user files and demands payment
   for the decryption key. Modern ransomware families (like LockBit, BlackCat, and
   WannaCry) encrypt files rapidly and alter file extensions. Traditional signature-
   based antivirus solutions cannot detect zero-day variants where cryptographic hashes
   are unknown. Existing heuristic tools that look only at high entropy generate
   intolerable false alarms on benign compressed files (.zip, .docx, .mp4).

5. Project Objectives:
   - Provide non-blocking, zero-latency local filesystem monitoring using Java NIO.
   - Accurately measure file randomness using Shannon entropy: H(X) = -sum(P(x) * log2 P(x)).
   - Implement sliding-window anomaly detection tracking modification rates and folder spans.
   - Prevent false positives on benign high-entropy files through multi-factor scoring.
   - Provide an active incident response engine with safe simulated containment.
   - Deliver an interactive JavaFX dashboard with live charts, telemetry, and audit logs.
   - Maintain persistent historical incident records in an embedded SQLite database.

6. What Makes This Project Useful & Different:
   Unlike naive solutions that flag any encrypted file, RansomShield combines content
   randomness with temporal activity patterns:
   - High Entropy ALONE = Score capped at 20/100 (remains NORMAL).
   - High Entropy + Rapid Modification Burst (e.g. 50 files/sec) + Suspicious Extension
     Renames (.encrypted) + Multi-directory Traversal = Score spikes to 85-100 (CRITICAL).
   This mathematical multi-heuristic defense eliminates false positives while detecting
   zero-day ransomware behaviour in sub-second time.

--------------------------------------------------------------------------------
3A. SHANNON ENTROPY
--------------------------------------------------------------------------------
1. What Entropy Measures:
   Shannon entropy measures the average amount of information, randomness, or
   uncertainty contained in a message or byte sequence.

2. Why It Detects Ransomware:
   Plaintext files (English text, source code, CSVs, XML) contain repetitive byte
   patterns (e.g., ASCII spaces, letter 'e', XML tags), resulting in low entropy (1.5 to 4.5).
   Cryptographic encryption algorithms (such as AES-256 or ChaCha20) output ciphertext
   that is statistically indistinguishable from uniform pseudorandom noise.
   Every byte value from 0 to 255 appears with almost equal probability (~1/256),
   causing Shannon entropy to spike close to the theoretical maximum of 8.0 bits/byte.

3. Mathematical Formula:
   H(X) = - SUM_{i=0}^{255} P(x_i) * log2( P(x_i) )

   Where:
   - X is the file byte data.
   - x_i is the i-th possible byte value (from 0 to 255, total 256 possibilities).
   - P(x_i) is the empirical probability of byte x_i occurring:
     P(x_i) = (Count of byte x_i) / (Total bytes read).
   - log2 is the logarithm to base 2. In Java: Math.log(P) / Math.log(2).

4. Why the Theoretical Range is 0.0 to 8.0 Bits per Byte:
   - Minimum: If a file contains only a single repeated byte (e.g., all 0x00 zeros):
     P(0) = 1.0, log2(1.0) = 0.
     H(X) = -(1.0 * 0) = 0.0 bits/byte.
   - Maximum: If all 256 byte values appear with equal frequency:
     P(x_i) = 1 / 256 for all 256 bytes.
     log2(1 / 256) = log2(2^-8) = -8.
     H(X) = - SUM_{i=0}^{255} (1/256 * (-8)) = - (256 * (1/256 * -8)) = 8.0 bits/byte.

5. What Entropy Levels Mean in Practice:
   - 0.0 – 3.0 bits/byte: Highly repetitive (sparse files, ASCII logs, empty tables).
   - 3.0 – 5.5 bits/byte: Standard natural language text, source code (.java, .txt, .c).
   - 5.5 – 6.8 bits/byte: Rich documents, uncompressed PDFs, compiled code (.class, .exe).
   - 6.8 – 7.5 bits/byte: Standard compressed archives (.zip, .gz, .docx, .png, .mp4).
   - 7.5 – 8.0 bits/byte: Cryptographically encrypted files, ransomware output, raw AES.

6. The False-Positive Dilemma:
   Compressed files (.zip, .mp4, .jpg) also have high entropy (> 7.5) because lossless
   compression algorithms (like DEFLATE) minimize redundancy. Therefore, high entropy
   by itself is NOT proof of ransomware! Flagging high entropy alone would generate false
   alarms whenever a user saves a Word doc (.docx is a ZIP) or downloads an image.

7. Numerical Walkthrough:
   Suppose a tiny file has 4 bytes: [ 'A', 'B', 'A', 'A' ]
   - Total bytes N = 4
   - Count('A') = 3 -> P('A') = 3/4 = 0.75
   - Count('B') = 1 -> P('B') = 1/4 = 0.25
   - log2(0.75) = ln(0.75) / ln(2) = -0.28768 / 0.69315 = -0.41504
   - log2(0.25) = ln(0.25) / ln(2) = -1.38629 / 0.69315 = -2.00000
   - H(X) = - [ 0.75 * (-0.41504) + 0.25 * (-2.00000) ]
          = - [ -0.31128 - 0.50000 ] = 0.81128 bits/byte.

8. Source Code Location & Excerpt:
   File: src/main/java/com/ransomshield/analysis/EntropyCalculator.java
   Method: computeEntropyFromFrequencies(long[] frequencies, long totalBytes) (lines 109-120):

   ```java
   private double computeEntropyFromFrequencies(long[] frequencies, long totalBytes) {
       double entropy = 0.0;
       for (long count : frequencies) {
           if (count > 0) {
               double p = (double) count / totalBytes;
               entropy -= p * (Math.log(p) / LOG_2); // LOG_2 = Math.log(2)
           }
       }
       // Clamp between 0.0 and 8.0 to eliminate minor floating-point inaccuracies
       return Math.max(0.0, Math.min(8.0, entropy));
   }
   ```
   Line-by-line explanation:
   - Line 110: Initializes accumulator variable entropy = 0.0.
   - Line 111: Iterates through the 256 possible byte frequency counts.
   - Line 112: If count == 0, that byte did not appear; skip it because 0 * log2(0) = 0.
   - Line 113: Computes probability p = count / totalBytes (cast to double).
   - Line 114: Computes -p * log2(p) using Java's Math.log(p) / Math.log(2) change of base.
   - Line 119: Math.max(0.0, Math.min(8.0, entropy)) guarantees numerical safety against
     IEEE 754 precision rounding.

3B. BEHAVIOURAL DETECTION & SLIDING-WINDOW ANALYTICS
--------------------------------------------------------------------------------
Implemented in com.ransomshield.analysis.BehaviorDetector.java.

The detector maintains:
- Deque<FileEvent> eventWindow: ConcurrentLinkedDeque storing all events within the last 5.0 seconds.
- Map<Path, FileActivityState> fileStates: ConcurrentHashMap tracking per-file history.

Metrics computed for each 5.0s window:
1. Modification Rate:
   Formula: (modifiedCount + renameCount) / max(1.0, durationSeconds).
   Measures operations per second to catch automated ransomware encryption loops.
2. Unique Files Touched:
   Count of distinct Path objects modified within the window.
3. Unique Directories Affected:
   Count of distinct parent folders touched (measures recursive directory traversal).
4. Operation Pattern & Suspicious Renames:
   Checks if the new file extension matches known ransomware extensions configured in
   application.properties (e.g., .encrypted, .locked, .crypto, .crypted, .wncry, .locky).

3C. MULTI-FACTOR THREAT SCORING ENGINE
--------------------------------------------------------------------------------
Implemented in com.ransomshield.analysis.ThreatScoreEngine.java (lines 25-141).

The final threat score is an additive composite score (0 to 100):
Total Score = EntropyScore + RateScore + FilesScore + DirectoryScore + OperationScore

Factor Breakdown (from actual source code):
+--------------------+-----------+-----------------------------------------------+
| Factor             | Max Pts   | Scoring Logic & Thresholds                    |
+--------------------+-----------+-----------------------------------------------+
| 1. Shannon Entropy | 20 pts    | >= 7.5 bits/byte (High)   -> 20 pts           |
|                    |           | >= 7.0 bits/byte (Medium) -> 10 pts           |
|                    |           | >= 6.0 bits/byte (Low)    -> 5 pts            |
|                    |           | < 6.0 bits/byte           -> 0 pts            |
+--------------------+-----------+-----------------------------------------------+

|                    |           | >= 5.0 files/sec (Medium) -> 10 pts           |
|                    |           | >= 2.0 files/sec (Low)    -> 5 pts            |
|                    |           | < 2.0 files/sec           -> 0 pts            |
+--------------------+-----------+-----------------------------------------------+
| 3. Unique Files    | 20 pts    | > 100 files (High)        -> 20 pts           |
|                    |           | >= 21 files (Medium)      -> 10 pts           |
|                    |           | > 5 files (Low)           -> 5 pts            |
|                    |           | <= 5 files                -> 0 pts            |
+--------------------+-----------+-----------------------------------------------+
| 4. Directory Span  | 10 pts    | >= 5 distinct directories -> 10 pts           |
|                    |           | 3 - 4 directories         -> 7 pts            |
|                    |           | 2 directories             -> 3 pts            |
|                    |           | 1 directory               -> 0 pts            |
+--------------------+-----------+-----------------------------------------------+

|    Pattern         |           | Suspicious rename (<10 files)  -> 10 pts      |
|                    |           | Mass rename/delete (>=10)      -> 7 pts       |
|                    |           | Repeated create/modify cycle   -> 3 pts       |
+--------------------+-----------+-----------------------------------------------+
| MAXIMUM RAW SCORE  | 90 pts*   | Clamped: Math.min(100, Math.max(0, total))    |
+--------------------+-----------+-----------------------------------------------+
*Note on discrepancy: The base factor weights sum to 90 points. Combined Mode 6
triggers 20 (entropy) + 20 (rate) + 10 (files: ~75) + 7 (dirs: 4) + 20 (pattern:
.encrypted rename) = 77 to 87 points, safely crossing the CRITICAL (80) or HIGH (60)
thresholds. Clamping ensures strict 0-100 normalization.

Severity Mapping (ThreatLevel.java):
- 0 to 29:   NORMAL      (Color: #10b981 Green)
- 30 to 59:  SUSPICIOUS  (Color: #f59e0b Amber)
- 60 to 79:  HIGH        (Color: #f97316 Orange)
- 80 to 100: CRITICAL    (Color: #ef4444 Red)

Worked Example:
Suppose a malicious script encrypts 40 files across 3 folders in 2 seconds with .locked:
- Max Entropy = 7.92 bits/byte (>= 7.5)                -> 20 points
- Modification Rate = 40 / 2 = 20 files/sec (> 15.0)   -> 20 points
- Unique Files = 40 files (between 21 and 100)         -> 10 points
- Directories = 3 folders (between 3 and 4)            ->  7 points
- Operation = 40 files renamed to .locked (>= 10)      -> 20 points
Total Threat Score = 20 + 20 + 10 + 7 + 20 = 77 points.
Severity Classification = HIGH (Triggering Prominent Alert & Simulated Containment).


--------------------------------------------------------------------------------
3D. FALSE-POSITIVE PREVENTION
--------------------------------------------------------------------------------
How RansomShield Prevents False Alarms:
1. Hard Cap on Single High-Entropy Events:
   Even if a user saves a completely encrypted or compressed archive (entropy = 7.99),
   the Entropy Factor yields at most 20 points.
   Because 20 < 30 (SUSPICIOUS threshold), the score remains in NORMAL.
   No alert is raised, no notification is sent, and no containment is triggered.
2. Multi-Signal Requirement:
   Elevating to SUSPICIOUS or CRITICAL requires simultaneous anomalous velocity
   (rate > 5 files/sec), multi-file burst, and suspicious file renames.
3. Demonstration:
   Mode 2 in the test simulator specifically writes a file with 7.9 bits/byte entropy.
   The dashboard displays: Entropy Factor = 20 pts, Total Score = 20/100 (NORMAL).

SECTION 7: IMPORTANT TECHNICAL QUESTIONS AND ANSWERS
================================================================================

Q1: What is ransomware?
A: Ransomware is malicious software that denies users access to their system or personal
   files by encrypting data and demanding a ransom payment in exchange for the decryption key.

Q2: Why is real-time behavioral detection better than signature-based antivirus?
A: Signature-based tools check cryptographic hashes (like SHA-256) of known malware files.
   Attackers easily bypass this using polymorphism, recompilation, or packing. Behavioral
   detection monitors what the program DOES (rapid modifications, high entropy, mass renames)
   rather than what it LOOKS LIKE, allowing it to stop zero-day attacks.

Q3: Why did you choose Java for this project?
A: Java provides cross-platform file monitoring via Java NIO.2, robust multithreading with
   high-level concurrent collections (LinkedBlockingQueue, ConcurrentHashMap), a modern native
   desktop GUI via JavaFX, and type safety with automatic garbage collection.

Q4: What is Shannon entropy and how does it work?
A: Formulated by Claude Shannon in 1948, it quantifies information uncertainty. In computing,
   it measures how uniformly byte values (0-255) are distributed across a file.
   Formula: H(X) = -SUM( P(x) * log2 P(x) ).

Q5: Why is the range of byte entropy specifically 0.0 to 8.0?
A: A byte has 8 bits, yielding 2^8 = 256 possible values. If all 256 values are equally likely
   (P = 1/256), the maximum uncertainty is log2(256) = 8.0 bits. If only one byte appears (P = 1.0),
   uncertainty is log2(1) = 0.0 bits.

Q6: Why does encryption produce high entropy?
A: Good cryptographic ciphers (like AES) produce ciphertext that passes all statistical tests
   for randomness (avalanche effect). Every byte from 0x00 to 0xFF appears with equal probability (~1/256).

Q7: Why does high entropy alone NOT prove that a file is encrypted by ransomware?
A: Lossless compression algorithms (like ZIP, JPEG, MP4, and DOCX) also remove redundant patterns,
   producing high entropy (7.2 to 7.8). Treating high entropy alone as proof of ransomware causes
   frequent false positives on ordinary files.

Q8: How does your BehaviorDetector work?
A: It maintains a sliding time window (5.0 seconds) in a ConcurrentLinkedDeque. As filesystem
   events arrive, they are recorded. A pruning algorithm removes events older than 5.0 seconds.
   The detector computes point-in-time metrics: modification rate, unique file count, directory
   span, and ransomware extensions.

Q9: How is the threat score calculated?
A: It is an additive score (0 to 100) combining 5 factors:
   1. Shannon Entropy (0-20 pts)
   2. Modification Rate (0-20 pts)
   3. Unique Files Touched (0-20 pts)
   4. Directory Traversal Span (0-10 pts)
   5. Operation Pattern / Rename to Known Ransomware Extension (0-20 pts).

Q10: What are your threat level thresholds?
A: NORMAL (0 to 29), SUSPICIOUS (30 to 59), HIGH (60 to 79), and CRITICAL (80 to 100).

Q11: What is a false positive and how does your project prevent it?
A: A false positive occurs when legitimate activity is flagged as malicious. RansomShield prevents
   this by capping the entropy factor at 20 points. Even a file with 8.0 entropy stays in NORMAL
   unless accompanied by anomalous speed, mass edits, or suspicious renames.

Q12: How does Java NIO WatchService work under the hood?
A: It hooks into native operating system file notification APIs — ReadDirectoryChangesW on
   Windows, inotify on Linux, and kqueue on macOS. When changes occur, the OS signals the
   WatchService, which returns WatchKey objects containing the change events.

Q13: Does WatchService automatically monitor subdirectories recursively?
A: No. In Java NIO, WatchService is not natively recursive. RansomShield overcomes this by
   using java.nio.file.Files.walkFileTree() to recursively register every subdirectory at startup,
   and dynamically registers new subdirectories in the ENTRY_CREATE event loop.

Q14: How does RansomShield detect file renames when WatchService doesn't have an ENTRY_RENAME event?
A: The OS emits an ENTRY_DELETE event followed by an ENTRY_CREATE event. FileMonitor sorts events
   to prioritize DELETEs, tracks recent deletions in a ConcurrentHashMap, and when a CREATE event
   arrives within 4 seconds in the same folder with the same base name, it correlates them into a RENAME.

Q15: Why is multithreading necessary in this application?
A: Filesystem events can arrive at hundreds of events per second during an attack. If entropy
   calculation or GUI updates ran on the monitoring thread, WatchService would overflow and drop events.
   We decouple monitoring, analysis, and UI into separate threads.

Q16: How do threads pass events safely without data races?
A: We use a thread-safe LinkedBlockingQueue<FileEvent>. The monitor acts as the producer calling
   queue.offer(), and a pool of 4 analysis daemon workers act as consumers calling queue.poll().

Q17: Why do you use Platform.runLater() for GUI updates?
A: JavaFX enforces a single-thread rule: only the JavaFX Application Thread may modify UI nodes.
   Background worker threads call Platform.runLater(Runnable) to schedule UI updates safely.

Q18: Why did you choose SQLite and JDBC?
A: SQLite is serverless, zero-configuration, and stores data in a single local file (ransomshield.db).
   JDBC is the standard Java Database Connectivity API. It allows seamless persistence of incidents
   and file events for forensic analysis.

Q19: What happens if the database is unavailable or locked?
A: All database operations use explicit try-catch blocks with logging. If an insert fails, the in-memory
   engine and JavaFX dashboard continue functioning without crashing.

Q20: How does your test simulator work?
A: It runs inside com.ransomshield.simulator.RansomwareSimulator and modifies files strictly
   inside the monitored test folder (./test-data). It generates synthetic signals (text appending,
   uniform pseudorandom bytes, rapid moves) without executing any real malicious code or shell scripts.

Q21: Why do you use a safe simulator instead of real ransomware?
A: Real ransomware could escape the test folder, destroy student or university files, infect the
   host operating system, or trigger enterprise antivirus blocks. A simulator reproduces the exact
   behavioural signals safely and reversibly.

Q22: Can your application identify the exact process (PID) that modified a file?
A: Standard Java NIO WatchService relies on OS filesystem notifications, which DO NOT deliver
   the Process ID (PID) or executable path. Attributing a file modification to a specific process
   requires kernel-level filter drivers (Windows Minifilter / ETW or Linux eBPF). RansomShield
   honestly acknowledges this limitation rather than guessing PIDs.

Q23: Does the application stop ransomware or only alert?
A: It implements Active Defence. In Safe Simulation Mode (default for college reviews), it simulates
   containment and logs the response. In live action mode, it supports sandboxed file quarantine,
   moving suspicious files to an isolated .quarantine/ directory.

Q24: What is the difference between file quarantine and process termination?
A: Quarantine isolates the affected files so they cannot be further tampered with. Process
   termination kills the running program responsible for the attack.

Q25: How do you prevent path traversal attacks in your QuarantineService?
A: QuarantineService normalizes every path and verifies targetPath.startsWith(normalizedScope).
   If a path contains relative escapes like "../../", it throws a SecurityException and aborts.

Q26: How does the threat score decay when an attack stops?
A: RansomShieldEngine runs a scheduled heartbeat thread every 1.0 second. It calls
   BehaviorDetector.pruneWindow(), discarding events older than 5.0 seconds. When events expire,
   the sliding-window metrics drop to zero, and the ThreatScoreEngine returns the score to NORMAL.

Q27: How could RansomShield be expanded into an enterprise EDR product?
A: By integrating kernel-level event tracing (Windows ETW / Sysmon or Linux eBPF) for reliable
   process attribution, connecting to Windows Volume Shadow Copies (VSS) for automated file recovery,
   and forwarding security alerts to a SIEM (like Splunk or Elasticsearch).

SECTION 8: LIMITATIONS AND FUTURE SCOPE
================================================================================

A. Current Implementation Limitations:
1. Process Attribution Limitation:
   Java NIO WatchService does not expose the Process ID (PID) or application executable
   that modified a file. Process containment is therefore simulated.
2. Kernel vs. User Space:
   Because RansomShield operates in user space, kernel-level rootkits or ransomware that
   disables user-space applications could theoretically terminate the JVM.
3. Cryptographic Decryption:
   Once a file is encrypted by real ransomware, it cannot be decrypted without the attacker's
   private key or a clean backup. RansomShield is a detection and containment shield, not a decryptor.
4. Rename Order Nuances:
   On certain operating systems, under extreme disk congestion, WatchService may drop events
   or reorder DELETE/CREATE pairs, leading to renames being recorded as separate creates and deletes.
5. High I/O Resource Utilization:
   Computing Shannon entropy on files larger than 25MB could cause CPU spikes; RansomShield
   mitigates this by sampling the first 25MB of large files.

B. Prioritized Future Scope:
1. Reliability & Robustness:
   - Implement native JNI/JNA hooks to Windows ETW (Event Tracing for Windows) and Linux fanotify
     to capture PIDs and process image paths directly with each I/O event.
2. Security Features:
